# EV Capture 5.5.9: static findings

> **LightRec release update (2026-10-14):** The historical AMF-only implementation notes and benchmarks below describe earlier experiments. The current portable build probes AMD AMF, Intel QSV, NVIDIA NVENC, and Windows Media Foundation hardware encoders at startup, then tries the next available backend if the selected hardware encoder fails during recording, with CPU encoding as the final fallback. The active and completion UI show the selected encoder backend. It is packaged as one x64 `LightRec.exe` with FFmpeg and the Python runtime embedded; the ZIP also includes this guide and third-party notices. A 64×64 probe falsely rejected hardware backends on this machine, so the current probe uses 640×360. On this Windows 11 Ryzen 7 6800H test PC, the updated one-file build recorded the actual desktop at 1920×1080, 20 FPS, HEVC/AMD AMF for 12.4 seconds (2,285,195 bytes; 1,473 kbps); that temporary sample was deleted. A separate three-second Desktop Duplication to HEVC/Media Foundation hardware-encoder path also exited successfully with no file output. Windows 10 and Intel Quick Sync on the user's i7-14700K have not yet been tested on their target hardware, so compatibility on that machine remains to be verified.

The compatibility basis is Windows 10 x64 and newer: the bundled runtime is built on Python 3.14, which supports Windows 10 and newer, and Windows Desktop Duplication is a desktop API available since Windows 8. This is a platform/API compatibility basis, not a claim that every display driver, remote desktop session, protected desktop, or display mode will work; Microsoft documents access and mode limitations for `DuplicateOutput`. Sources: [Python supported Windows versions](https://docs.python.org/3.14/using/windows.html#supported-windows-versions), [Microsoft Desktop Duplication API](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nn-dxgi1_2-idxgioutputduplication), and [DuplicateOutput requirements and errors](https://learn.microsoft.com/en-us/windows/desktop/api/DXGI1_2/nf-dxgi1_2-idxgioutput1-duplicateoutput).

Target: `EVCapture_v5.5.9.exe`, supplied in the workspace. The installer and extracted main executable both have valid Authenticode signatures from Hunan Yiwei Information Technology Co., Ltd. The installer stub is x86; the extracted `EVCapture.exe` is x64. The recorder application itself is a Qt 5 application, not an x86 program.

The installer was inspected with Inno Setup extraction without launching either installer or recorder. The extracted recorder was not executed. Findings below come from the signed installer contents, PE imports/exports, embedded strings, the bundled FFmpeg diagnostic output, and the vendor's help pages.

## What the files show

- `EVCapture.exe` imports Qt 5 and FFmpeg libraries (`avcodec-58.dll`, `avformat-58.dll`, `avutil-56.dll`, `avfilter-7.dll`, `avdevice-58.dll`), plus `evc_video_encoder.dll`. It imports `avcodec_find_encoder` and `av_codec_is_encoder`.
- Its strings include separate recording settings `Output.RecordVideoQualityLevel`, `Output.RecordVideoEncodeLevel`, `Output.RecordHardwareEncoderEnabled`, `Output.RecordGpuConversionEnabled`, and `Output.RecordAudioBitrate`, plus six `Quality1`–`Quality6` UI entries. This confirms separate quality, speed-level, hardware-encoder, GPU-conversion, and audio controls exist; it does not reveal their current values.
- `Output.StreamVideoEncodeLevel` appears separately beside the strings `superfast`, `faster`, `medium`, and `ultrafast`. These preset names are associated with the streaming setting in the binary string table; they do not establish which choices or default map to the recording screenshot's “编码级别：默认”.
- `evc_video_encoder.dll` exposes separate `EvcGpuEncoder` and `EvcSwEncoder` classes, plus an `is_hardware` method. This is direct evidence that the application has distinct hardware and software encoder paths.
- The installer includes three vendor-specific encoder modules: `evc_amf.dll`, `evc_nvenc.dll`, and `evc_qsv11.dll`. Their imports/strings point to AMD AMF, NVIDIA NVENC and Intel oneVPL/QSV. The NVENC module links D3D11/DXGI and contains `EncodeTexture` symbols.
- The AMF module contains properties for target and peak bitrates and `QvbrQualityLevel`; QSV strings include `ICQ Quality` and `HQVBR`. This shows the bundled backends can use quality/rate-control settings. It does **not** prove which specific rate mode EV chooses for a given recording preset.
- The bundled FFmpeg is `git-2019-10-22`, with libx264/libx265 plus H.264/HEVC AMF, NVENC and QSV encoders and AAC audio. The media stack is therefore old and vendor-supplied, with an application layer choosing among software and hardware backends.
- The included release notes say hardware-accelerated recording was added in 5.2.3 and had further optimization in 5.4.9. The 5.5.9 installer contains encoder modules and the hardware toggle above. Vendor docs say the hardware option must be selected manually.

EV's public help material gives more direct guidance on its size/quality tradeoff: its six image-quality levels run from original quality down to ordinary quality, with file size falling as the level is lowered; it recommends roughly 7–10 FPS for lecture videos and 20+ FPS for fast motion, and separately identifies frame rate, scene changes, duration and frame dimensions as file-size factors. It recommends 128–192 kbps audio for everyday use. These recommendations make workload-matched frame rate, video quality and audio bitrate credible parts of the small-file result. They do not reveal the exact codec, QP, bitrate, or preset that EV's encoder applies internally. Sources: [quality and capture settings](https://www.ieway.cn/help/desc-evcapture-pc-106.html), [parameter recommendations](https://www.ieway.cn/help/desc-evcapture-pc-543.html), [file-size guidance](https://www.ieway.cn/help/desc-evcapture-pc-228.html).

## What makes “small but clear” plausible

There is no single magic compression trick. EV exposes a quality level and hardware-encoder choice; its encoder modules expose variable/quality-based bitrate controls; the vendor also recommends matching frame rate and capture area to the content. Hardware encoding mainly lowers CPU cost. The codec and rate control determine the size/quality tradeoff. LightRec's first prototype used QVBR, but its file size varied too much to target the user's EV example. The current implementation uses a selectable total CBR target and defaults to 1,400 kbps.

FFmpeg 8.0's `ddagrab` outputs D3D11 hardware frames and AMF accepts D3D11 frames. Direct encoding initially failed because the capture and encoder were initialized on separate hardware contexts. Initializing `d3d11va=dev:0`, deriving `amf=amf@dev`, and assigning the same device to the filter graph made direct texture input work on this AMD system. HEVC accepts the captured texture directly; H.264 required a D3D11 `scale_d3d11=format=nv12` conversion in a separate short run. LightRec now tries these GPU-resident paths first, with the prior `hwdownload,format=bgra,format=yuv420p` CPU conversion retained as an early-failure compatibility fallback. See FFmpeg 8.0 [`ddagrab`](https://github.com/FFmpeg/FFmpeg/blob/n8.0/libavfilter/vsrc_ddagrab.c) and [AMF encoder input handling](https://github.com/FFmpeg/FFmpeg/blob/n8.0/libavcodec/amfenc.c).

The earlier LightRec prototype used AMD AMF QVBR at level 23. AMD documents QVBR as spending more bits on complex scenes and fewer on simple ones; that behavior produced inconsistent file sizes on our workload and did not by itself match the EV size estimate. The current code uses AMF `transcoding` usage with a CBR target and HRD filler. The AMD docs describe encoder capabilities; they do not prove EV uses QVBR or CBR. See AMD's [rate-control guide](https://github.com/GPUOpen-LibrariesAndSDKs/AMF/wiki/Rate-Control-Methods) and [HEVC encoder API](https://github.com/GPUOpen-LibrariesAndSDKs/AMF/blob/master/amf/doc/AMF_Video_Encode_HEVC_API.md).

FFmpeg documents `ddagrab` as a Desktop Duplication capture filter and describes `dup_frames` as repeating frames when there are no new frames. LightRec now defaults to repetition enabled so its output follows the selected FPS; the optional skip-unchanged setting instead produces variable-frame-rate output. This behavior is from the FFmpeg filter, not evidence of EV's internal capture path. See the [FFmpeg filter source documentation](https://ffmpeg.org/doxygen/trunk/vsrc__ddagrab_8c_source.html).

## AMF preset and target-size experiment

To isolate the encoding preset, a temporary on-screen synthetic desktop UI was animated at 20 Hz; FFmpeg output was sent to its null muxer, so no video file was retained and no frames were viewed. All runs used 1920×1080, `ddagrab`, the same CPU `hwdownload,format=bgra,format=yuv420p` conversion, HEVC AMF, and a 10-second media duration.

The old `-usage high_quality -quality quality -rc qvbr -qvbr_quality_level 23` path produced 178 frames in 12.08 seconds (0.823× real time), about 1,497 KiB of encoded video, about 0.94 CPU core, and 408 MiB maximum RSS. Changing only the AMF usage to `transcoding` while keeping `-quality quality` and QVBR 23 produced 200 frames in 10.03 seconds (0.992× real time), but only 259 KiB; CPU fell to about 0.33 core and RSS to 198 MiB. `transcoding/balanced` was similarly fast and small (260 KiB, about 0.18 core). This identifies `high_quality` usage as the dominant cost and size multiplier; the quality preset had little effect under `transcoding` on this workload.

QVBR alone did not meet the EV example's average size on this low-motion synthetic screen: `transcoding/quality` at QVBR 23 used 259 KiB, and QVBR 51 used 448 KiB over 9.95 seconds. Setting a 1,280 kbps CBR target without HRD/filler still averaged only about 0.61 Mbps. Enabling `-enforce_hrd true -filler_data true` made the target effective: it emitted 200 frames over 9.95 seconds, about 1,564 KiB (1.29 Mbps), in 10.04 seconds, at about 0.19 CPU core and 175 MiB maximum RSS. No audio was used in this test.

Based on that measurement, LightRec's code now uses AMF `transcoding/quality` plus CBR with HRD/filler, defaults to 1,400 kbps total, and subtracts the selected audio bitrate from the video target when system audio is enabled. That gives a 1,272 kbps video target with 128 kbps audio, approximately matching the EV example's 1.4 Mbps total. The UI now defaults to emitting the selected frame rate; skipping unchanged frames is optional. This is a size-and-throughput match, not proof of visual equivalence to EV's “1 原画” preset. The profile is based on a synthetic low-motion workload, and CBR can show more compression on unusually complex scenes.

## Limits of the evidence

This static pass does not prove EV's default codec, the exact quality-level-to-QP/QVBR mapping, chroma format, capture API path, texture-copy behavior in its own code, or post-recording transcode parameters. Strings and available DLL properties prove capability, not a specific runtime choice. Capturing a real sample and comparing it with FFprobe plus SSIM/VMAF would be needed to validate the observed size/quality tradeoff. Full native disassembly would need a configured analysis engine; no Ghidra or IDA was available in this environment.

A further inventory of the extracted installation found no shipped `.ini`, `.json`, `.xml`, or similar sidecar settings file to reveal the quality-level mapping. The installer contains runtime DLLs and release notes, but no standalone preset table that changes the limits above.

The i7-14700K migration target includes Intel UHD 770 graphics and Quick Sync but has no discrete GPU. The previous implementation selected QSV yet always downloaded Desktop Duplication frames to system memory before the hardware encoder uploaded them again. LightRec now attempts to derive a QSV device from the same D3D11 device used by `ddagrab`, keeping frames GPU-resident. If this direct path fails during startup, the existing retry switches to the compatible download/upload path with the same QSV encoder. FFmpeg documents deriving QSV from a D3D11 device and DDA's D3D11 frame output. This target hardware is not available here, so QSV direct-path startup, CPU load, file size and long-duration behavior still require verification on the i7-14700K computer.
